# 080 — Flutter: runtime configuration, Cognito, and the hello call

**Status note:** Requirements 1, 2, 3, 5 and 6 are delivered (2026-09-27): `HelloService` calls `GET /api/v1/hello` with the id token when Amplify is configured and without one under `SKIP_AUTH`, and the "+" action shows the answer. `make go-run` now allows the `:3000` origin.

Requirements 4, 4a, 4b and 7 are delivered (2026-10-08). `scripts/ui-config.sh` takes `ENV` and writes both files; the two carry the same values under different key names, because web fetches camelCase JSON at startup and mobile reads define names baked in at build time. The mobile run and build targets pass `--dart-define-from-file=config/$(ENV).json`, and `SKIP_AUTH` now defaults to `false` for every deployed backend. Before this, the mobile targets passed `SKIP_AUTH` and `API_BASE_URL` alone, so the three Cognito defines were empty and `SKIP_AUTH=false` showed the "not configured" widget instead of the Authenticator: there was no path to real mobile sign-in at any flag setting.

Open: the acceptance criteria that need a sign-in on web, Android and iOS. Only the operator can run those, on their own devices.

**Complexity:** Medium
**Risk:** Medium — a wrong config path on web breaks the app silently; token handling must send the id token the Go service expects.
**Estimated cost:** ~1 day
**Recommended model:** Sonnet.
**Depends on:** 070-flutter-shell-trim, 055-cognito-and-token, 020-go-hello-service
**Lifecycle class(es) touched:** None.

## Scope

Move every environment value out of source: the app reads its API base
URL and Cognito identifiers at startup (web) or from a build-time define
file (mobile). Then wire the "+" button to `GET /api/v1/hello` and show
the answer.

Excludes: the Cognito pool (the platform's spec AWS-035), the ConfigMap that serves `config.json`
in the cluster (040/060), platform folders (100).

## Requirements

1. `lib/src/config/app_config.dart` MUST expose `AppConfig.load()` returning `apiBaseUrl`, `cognitoUserPoolId`, `cognitoClientId`, `cognitoRegion`. On web it fetches `Uri.base.resolve('config.json')`. On other platforms it reads `String.fromEnvironment` for `API_BASE_URL`, `COGNITO_USER_POOL_ID`, `COGNITO_CLIENT_ID`, `COGNITO_REGION`.
2. The Amplify configuration JSON MUST be built at runtime from `AppConfig` (move the template from `lib/amplifyconfiguration.dart` into a function; delete the hardcoded pool `eu-west-1_iRYFPY5Xv` and client id).
3. When any value is missing, the app MUST show an `ErrorStateWidget` with the missing key names instead of the Authenticator.
4. `flutter-ui/web/config.json` MUST carry local defaults: `apiBaseUrl: http://localhost:8080`, empty Cognito values. It MUST be gitignored, not committed. `flutter-ui/config/*.json` MUST be gitignored; `make ui-config ENV=<env>` writes `flutter-ui/config/<env>.json` from `/$(PROJECT_NAME)/persistent/ahorro-cognito` (055; there is no `make tf-outputs`, this repository holds no Terraform). *(Amended twice. First: this requirement said `web/config.json` MUST be committed. One Cognito pool exists per platform project, so a committed copy is right for one project and wrong for every other — the file is generated by `make ui-config` every time. Second: `ENV` was the single value `lab`, naming the one deployed backend that existed. See 4a.)*

4a. `ENV` MUST be one of `local` (the default), `dev`, `prod` or `pr-<n>`, and it MUST set `API_BASE_URL` in the define file to `http://localhost:8080`, `https://api-ahorro-dev.<fqdn>`, `https://api-ahorro.<fqdn>` or `https://api-ahorro-pr-<n>.<fqdn>`. Any other value MUST fail and name the four. `<fqdn>` comes from `FQDN=` when set, else from the platform's `/$(PROJECT_NAME)/cluster/ahorro-deploy/fqdn`; `make down` deletes that parameter, so the override is what regenerates a config with the lab off. *(Added: three namespaces now serve the application — `ahorro`, `ahorro-dev` and `ahorro-pr` — and one `ENV` value cannot name them.)*

4b. `ENV` MUST steer `flutter-ui/web/config.json` and `flutter-ui/config/<env>.json` alike, so the browser and the device reach the same backend. Every deployed `ahorro-api` MUST therefore accept `http://localhost:3000` as a CORS origin beside its own web host — the port `make ui-run-web` serves on — in `gitops/values.yaml` for `ahorro`, in `scripts/deploy-dev.sh` for `ahorro-dev` and in `scripts/preview.sh` for a preview. *(Amended. This requirement first said the opposite: `ENV` changed mobile only, and web kept naming the local API, because a deployed API allowed one origin and a browser on `localhost:3000` was blocked. The operator asked for the same behavior on every platform, and the CORS grant turned out to cost nothing here. See 4c.)*

4c. The grant in 4b is sound only while no credential travels on its own. This API reads `Authorization: Bearer`, the token lives in per-origin `localStorage` that a page on another origin cannot read, and `httpx.CORS` sets no `Access-Control-Allow-Credentials`, so no cookie is sent cross-origin. A move to cookie sessions would turn the grant into a CSRF hole, so `TestCORSSetsNoCredentialsHeader` MUST fail if that header is ever set. *(Added: the reasoning the grant rests on, with a test rather than a comment, because the condition can be broken by a change somewhere else entirely.)*
5. `lib/src/services/hello_service.dart`: `Future<String> hello()` does `GET $apiBaseUrl/api/v1/hello` with `Authorization: Bearer <id token>` from `Amplify.Auth.fetchAuthSession()` and `X-Request-Id` from `OperationIdService`, logs through `ApiLogger`, and throws a typed error on non-200.

5a. `ApiLogger` MUST print the request id on one line per call at the `info` level, beside the method, the URL and the status, and `info` MUST be the default level. *(Added: the id reached the console only inside the `verbose` header dump, so correlating a tap with a service log line meant raising the level and reading pages of headers. The service already logs `request_id` as a JSON field, so the two sides now match on one line each. `kDebugMode` still gates every line, so a release build prints nothing.)*
6. The "+" action MUST call `HelloService.hello()` and show the returned message through `MessageUtils.showMessageSafely` (SnackBar on Android and web, Cupertino alert on iOS). Errors show the same way with the status code.
7. Mobile run and build targets MUST pass `--dart-define-from-file=config/$(ENV).json` (100 defines the targets).

## Implementation hints

- `Uri.base.resolve('config.json')` respects `<base href>`; keep `$FLUTTER_BASE_HREF` in `web/index.html`.
- `AppConfig.load()` runs before `runApp` in `main()`; pass the result down with `Provider`.
- The id token is at `(session as CognitoAuthSession).userPoolTokensResult.value.idToken.raw` — the same expression the old `api_service.dart` used.

## Testing / acceptance criteria

- Unit test: `HelloService.hello()` against a `MockClient` asserts the `Authorization` and `X-Request-Id` headers and parses `message`.
- Web: `make go-run` (auth disabled) + `make ui-run-web` with the generated `web/config.json` → tap "+" → SnackBar "Hola, anonymous". *(Amended: the greeting is Spanish since `cf648aa`, and the target is `make ui-run-web`, which generates the file first.)*
- `scripts/ui-config.sh` for each of `local`, `dev`, `prod` and `pr-<n>` writes the four `API_BASE_URL` values of requirement 4a, and any other `ENV` exits 1. *(Verified 2026-10-08 with `FQDN=` and no AWS credentials.)*
- A generated `flutter-ui/config/<env>.json` carrying the domain leaves `make domain-check` green, because `scripts/domain-guard.sh` greps tracked files only. *(Verified 2026-10-08: a plain `grep -r` finds a marker domain in the generated file, and the guard reports clean.)*
- `make ui-test` and `make ui-analyze` stay green. Neither takes a define file, so the `ui` job in CI, which has no AWS access, is unaffected. *(Verified 2026-10-08: "No issues found!" and 15 tests passed.)*
- `AppConfig.load()` on a non-web platform reads the key names `scripts/ui-config.sh` writes. The two must not drift: a renamed key becomes an empty define inside an APK, which the app reports as an unconfigured pool. *(Verified 2026-10-08 against a `config/dev.json` generated from the live lab: `apiBaseUrl` carried the `api-ahorro-dev` host, the pool and client ids were non-empty, the region was `eu-west-1`, and `skipAuth` was false. Run with a throwaway test, which was then deleted — it cannot live in `flutter-ui/test/`, because the `ui` job in CI has no AWS access and so cannot generate the file it needs.)*
- `make ui-run-android` with no `ENV` still reaches `make go-run` on this machine with auth skipped. The working local loop must not regress.
- Unit test: `ApiLogger.logResponse` prints the status and `request_id=<id>` on one line, omits the label when no id is given, and prints at all with no `LOG_LEVEL` define. `logError` carries the id too. *(Verified 2026-10-08, including a mutation check: removing the id from the line fails two of the four.)*
- Lab, Android and iOS: `make ui-run-android ENV=dev` and `make ui-run-ios ENV=dev` → sign up and sign in with the Authenticator against the platform's pool, tap "+", see "Hola, <email>". The console prints one `request_id=<id>` line with no extra flag, and the same id appears in the service log — in Grafana, `{namespace="ahorro-dev", container="ahorro-api"} | json | request_id = "<id>"`.
- Lab, web: `make ui-run-web ENV=dev` → the same sign-in and the same answer in Chrome on `:3000`, with no CORS error in the console. Opening the deployed client at its own hostname does the same without this machine.
- `grep -rn "eu-west-1_\|AppClientId\"" flutter-ui/lib` returns nothing.
